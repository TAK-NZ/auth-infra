# Scoped Authentik Service Accounts

## Why this exists

Consumer applications (TAKTeamManager, CloudTAK) originally authenticated to
Authentik's REST API using the same superuser bootstrap admin token that this
stack uses internally for its own setup automation (OIDC provider setup,
enrollment, LDAP outpost provisioning). That token can create, modify, or
delete *anything* in Authentik — other admin accounts, providers, outposts,
flows, blueprints — none of which either consumer app needs or should be able
to touch.

This stack now provisions a dedicated, non-superuser Authentik **service
account** per consumer app, each restricted to a role holding only the
permissions that app's code actually calls. This follows the same blueprint
pattern already used for the LDAP outpost's `ldapservice` account
(`authentik/blueprints/tak-ldap-setup.yaml`), just applied to application
credentials instead of infrastructure credentials.

Reducing a token's privilege does not fix application-level bugs (e.g. a
credential can still misuse the permissions it *does* have). It reduces the
blast radius of a leaked or misused credential — with the superuser token, a
bug or leak in either consumer app could affect the entire Authentik
instance; with a scoped token, it's confined to the object types below.

## How it's provisioned

Each service account is created by a blueprint YAML file under
`authentik/blueprints/`, baked into the Authentik server/worker Docker image
at build time (`COPY authentik/blueprints/* /blueprints/tak/` in
`docker/authentik-server/Dockerfile.tak-nz`) and applied automatically by
Authentik's blueprint system on startup, or whenever the file's content hash
changes on a later deploy.

Each blueprint:

1. Creates an `authentik_rbac.role` holding a fixed, explicit list of global
   permissions (see below).
2. Creates an `authentik_core.user` of type `service_account`, assigned that
   role. The `state: created` marker means Authentik only creates this once
   — it will not be recreated or have its type/role reset if it's later
   modified by hand, so credential rotation doesn't get clobbered by a
   redeploy.
3. Creates an `authentik_core.token` (`intent: api`, non-expiring) for that
   user, with its `key` set from a CDK-generated value passed in via an
   environment variable (`!Env` blueprint context). This is different from
   the LDAP outpost's token, which Authentik generates internally and a
   separate Lambda (`LdapTokenRetriever`) has to retrieve after the fact —
   application API tokens can have their value set directly in the
   blueprint, so no retriever Lambda is needed for these.

The token's value is generated by CDK as a Secrets Manager secret
(`lib/constructs/secrets-manager.ts`), fed into the worker container as the
`AUTHENTIK_BOOTSTRAP_*_TOKEN` env var the blueprint reads, and exported as a
CloudFormation output for the consuming app's own CDK stack to import.

| App | Blueprint | Service account username | Secret name | CFN export |
|---|---|---|---|---|
| TAKTeamManager | `tak-teammanager-setup.yaml` | `tak-teammanager-service` | `{stackName}/Authentik/TeamManager-API-Token` | `AuthentikTeamManagerTokenArn` |
| CloudTAK | `tak-cloudtak-setup.yaml` | `tak-cloudtak-service` | `{stackName}/Authentik/CloudTAK-API-Token` | `AuthentikCloudTakTokenArn` |

## Granted permissions

### TAKTeamManager (`TAKTeamManager Service Role`)

| Permission | Why |
|---|---|
| `authentik_core.view_user` | List/lookup users by username, email, pk |
| `authentik_core.add_user` | Create internal users and BCH service accounts |
| `authentik_core.change_user` | Push local-authoritative attribute/name/status changes |
| `authentik_core.delete_user` | Orphan cleanup, service-account teardown |
| `authentik_core.view_group` | List/lookup channel, team, and agency groups |
| `authentik_core.add_group` | Create team/BCH/region/vendor/deployment/agency groups |
| `authentik_core.change_group` | Rename/update group attributes |
| `authentik_core.delete_group` | Delete channel/group objects |
| `authentik_core.add_user_to_group` | Add members to any of the above groups |
| `authentik_core.remove_user_from_group` | Remove members, including bulk removal |
| `authentik_core.view_token` | List tokens (device-enrollment app passwords) |
| `authentik_core.add_token` | Create device-enrollment app-password tokens |
| `authentik_core.delete_token` | Compensating delete on enrollment failure |
| `authentik_core.view_token_key` | Read back a created token's plaintext key (the only way to hand it to the enrolling device) |

No permissions on Applications, Providers, Outposts, Flows, Stages, Policies,
or Blueprints are granted — TAKTeamManager's code never calls those
endpoints.

**Known limitation, not fixed by this token:** Authentik forces any token
created via `POST /core/tokens/` by a non-superuser caller to be owned by the
caller itself (`authentik/core/api/tokens.py`,
`TokenViewSet.perform_create`). TAKTeamManager's device-enrollment flow
creates an app-password token *for a different user* (the enrolling device's
account), which this scoped token cannot do — the `user` field would be
silently overridden to the service account itself. This is a TAKTeamManager
code change, not a permissions gap; see that repo's own migration notes for
the recommended fix (use `POST /core/users/service_account/`, which creates
the user and its token atomically and isn't subject to this restriction).

### CloudTAK (`CloudTAK Service Role`)

| Permission | Why |
|---|---|
| `authentik_core.view_user` | List/lookup users and machine users by email/username/pk |
| `authentik_core.add_user` | Create machine (service-account) users |
| `authentik_core.add_token` | Required alongside `add_user` by `POST /core/users/service_account/` — see note below |
| `authentik_core.delete_user` | Delete machine users on connection teardown |
| `authentik_core.reset_user_password` | Set/rotate machine-user passwords; temp-password cert-enrollment fallback |
| `authentik_core.view_group` | List agencies and channels (both modeled as groups) |
| `authentik_core.add_user_to_group` | Attach a machine user to a channel group |

No permissions on Applications, Providers, Outposts, Flows, Stages,
Policies, Tokens (beyond `add_token`, see below), or Blueprints are granted.
CloudTAK's deploy-time OIDC provider/application setup uses a separate,
already-existing credential (the `cloudtak-oidc-setup` Lambda's own secret)
and is unrelated to this token.

**Why `add_token` is granted despite CloudTAK never listing or reading
tokens directly:** CloudTAK's `createMachineUser()` calls
`POST /core/users/service_account/`, Authentik's dedicated endpoint for
creating a service-account user and its initial app-password token in one
atomic call. That endpoint is guarded by
`@permission_required(None, ["authentik_core.add_user", "authentik_core.add_token"])`
— both permissions are required on the *same* request, even though the
created token always belongs to the newly-created user, never to an
arbitrary existing one. This was found and fixed after the role initially
shipped without `add_token`, which caused `createMachineUser()` to fail with
403 — verified by calling the real endpoint with the live scoped token
against the demo stack.

## Consuming these tokens from an application's own CDK stack

The pattern mirrors how this stack's own Lambdas consume the admin token
(`enroll-oidc-setup.ts`, `ldap-token-retriever.ts`):

1. Import the relevant secret's ARN via `Fn.importValue`, using this stack's
   `{stackName}-Authentik{App}TokenArn` export name convention (see
   `lib/cloudformation-imports.ts` for the shared import-name helper used
   elsewhere in this repo).
2. Resolve it with `secretsmanager.Secret.fromSecretCompleteArn(...)`.
3. Grant read access to the consuming ECS task's role:
   `secret.grantRead(taskRole)`.
4. Inject it into the container as an `ecs.Secret.fromSecretsManager(...)`
   environment variable, the same way `AUTHENTIK_BOOTSTRAP_TOKEN` is injected
   into the Authentik worker in `lib/constructs/authentik-worker.ts`.

Do **not** reuse `AuthentikAdminTokenArn` for either app going forward — that
export remains for this stack's own internal automation only.

## Adding a new scoped service account for another consumer app

1. Read the consuming app's Authentik API call sites and determine the
   *minimum* set of object types and actions it actually calls. Don't guess
   — verify against source, and where practical, verify against a live
   Authentik instance by calling the endpoint with a token that only holds
   the permission you intend to grant, and confirm both that it succeeds and
   that a deliberately withheld permission is rejected with 403.
2. Add a new secret in `lib/constructs/secrets-manager.ts` following the
   existing `teamManagerApiToken`/`cloudTakApiToken` pattern.
3. Add it to `SecretsConfig.authentik` in `lib/construct-configs.ts`.
4. Inject it into the worker container in
   `lib/constructs/authentik-worker.ts` as a new
   `AUTHENTIK_BOOTSTRAP_<APP>_TOKEN` secret.
5. Add a new blueprint file `authentik/blueprints/tak-<app>-setup.yaml`
   following the structure of the two existing app blueprints — role with an
   explicit permission list, `state: created` service account, `intent: api`
   token reading its key from the new `!Env` context var.
6. Wire the new secret through `lib/auth-infra-stack.ts` and
   `lib/outputs.ts` as a new exported CloudFormation output,
   `Authentik<App>TokenArn`.
7. Prefix the blueprint's `metadata.name` with `TAK - `, matching this
   stack's convention for distinguishing its own blueprints from Authentik's
   built-in `Default - ` ones in the console's blueprint list.
8. After deploying, if the blueprint instance already exists from a prior
   deploy under an old name, re-applying the blueprint updates its content
   and `metadata.name` but **not** the console-visible `name` field —
   Authentik only sets that field on first creation. PATCH it directly via
   `POST /api/v3/managed/blueprints/{pk}/` with both `name` and `path` in
   the body (the serializer requires `path` or `content` to be present on
   any write, even a rename-only PATCH).

## Operational notes

- **Blueprint changes require a stack redeploy to take effect**, because the
  files are baked into the Docker image, not mounted at runtime. A content
  change produces a new image hash, which CDK rebuilds and pushes on the
  next `cdk deploy`.
- **Discovery has up to an hour of lag.** Authentik's `blueprints_discovery`
  task runs on an hourly schedule by default. A newly changed blueprint
  file won't be re-applied until that schedule fires, unless manually
  triggered. To force it immediately after a deploy, find the schedule's ID
  and call `POST /api/v3/tasks/schedules/{id}/send/` with an admin token.
- **`GET /api/v3/managed/blueprints/available/`** lists every blueprint file
  found on disk, including ones with no corresponding
  `BlueprintInstance` row yet — useful for confirming a new file was picked
  up by the image build even before discovery has run.
- Applying multiple blueprints at the same moment (e.g. right after forcing
  discovery) can occasionally hit a transient Postgres deadlock on a shared
  table (observed on `authentik_policies_policybindingmodel`). This shows up
  as a blueprint instance briefly reporting `status: error` with an
  `OperationalError: deadlock detected` in its task log; re-applying that
  one instance (`POST /api/v3/managed/blueprints/{pk}/apply/`) clears it.
